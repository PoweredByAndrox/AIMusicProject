# Строгий промпт для анализа проекта и отбора идей

## Задача

{НАПИШИ_ЗАДАЧУ_ЗДЕСЬ}

Ты должен провести строгий анализ проекта и предложить только реально полезные идеи для улучшения.  
Не придумывай абстрактные советы. Не повторяй уже реализованные механизмы. Не предлагай идеи, которые нельзя проверить экспериментом.

Все ответы, таблицы, выводы, комментарии и планы пиши только на русском языке.

Перед анализом обязательно прочитай `AGENTS.md`, ключевую документацию проекта, конфиги сборки, тестовые файлы и файлы, напрямую связанные с задачей. Не начинай генерацию идей до фактического осмотра файлов.

---

## Обязательный процесс

### 1. Изучи источник правды по проекту

Сначала обязательно изучи реальные файлы проекта, документацию, конфиги, тесты, архитектурные заметки и другие source-of-truth материалы.

После этого кратко опиши:

- текущую архитектуру проекта;
- основные цели проекта;
- слабые места;
- уже существующие механизмы;
- какие решения уже реализованы частично или полностью.

Нельзя делать выводы только по памяти, названию файлов или предположениям.

---

### 2. Сгенерируй 20–30 сырых идей

Сгенерируй от 20 до 30 сырых идей по улучшению проекта.

Сгруппируй идеи по категориям, например:

- архитектура;
- качество кода;
- тестирование;
- производительность;
- UX/UI;
- безопасность;
- надёжность;
- наблюдаемость и логирование;
- автоматизация;
- документация;
- ML/AI/алгоритмы, если применимо.

---

### 3. Присвой статус каждой сырой идее

Для каждой сырой идеи обязательно укажи один статус:

```txt
KEEP / REJECT / MERGE / DEFER
```

Где:

- `KEEP` — идея достаточно сильная и идёт дальше в анализ;
- `REJECT` — идея отклонена;
- `MERGE` — идея объединяется с другой, более сильной или более общей идеей;
- `DEFER` — идея потенциально полезная, но сейчас не подходит для реализации.

---

### 4. Объясни причины для REJECT / MERGE / DEFER

Для каждой идеи со статусом `REJECT`, `MERGE` или `DEFER` укажи точную причину.

Используй только эти причины:

```txt
already exists
duplicate
too generic
not testable
too expensive
low impact
high risk
needs missing data
weaker than another idea
```

Если причина на английском, дополнительно объясни её по-русски.

Пример:

```txt
REJECT — too generic: идея слишком общая, нет понятного эксперимента и критерия успеха.
```

---

### 5. Оставь только 8–12 серьёзных идей

После фильтрации оставь только 8–12 сильных идей.

Эти идеи должны быть:

- конкретными;
- проверяемыми;
- потенциально полезными;
- реализуемыми в рамках проекта;
- не дублировать уже существующие механизмы;
- иметь понятный критерий успеха.

---

### 6. Для каждой серьёзной идеи сделай scoring matrix

Для каждой серьёзной идеи оцени:

```txt
Impact: 1–10
Feasibility: 1–10
Novelty: 1–10
Testability: 1–10
Risk: 1–10, где выше = хуже
TestCost: 1–10, где выше = хуже
```

Используй формулу:

```txt
Total =
Impact * 0.30 +
Feasibility * 0.20 +
Novelty * 0.15 +
Testability * 0.20 -
Risk * 0.10 -
TestCost * 0.05
```

Не ранжируй идеи только по ощущениям. Сначала посчитай `Total`.

---

### 7. Для каждой серьёзной идеи добавь проверку по проекту

Для каждой серьёзной идеи укажи:

```txt
already implemented: yes / partial / no
exact files/docs proving it
exact missing gap
```

Требования:

- указывай конкретные файлы, документы, тесты или конфиги;
- не пиши “возможно реализовано” без доказательства;
- если доказательства нет — пиши, что доказательство не найдено;
- если механизм уже существует, объясни, чего именно не хватает.

---

### 8. Для каждой серьёзной идеи сделай novelty / prior-art check

Для каждой идеи проверь новизну и наличие похожих подходов.

Укажи:

```txt
related known method/tool/paper if relevant
what already exists
what is different here
novelty risk: low / medium / high
```

Если идея не новая — это не обязательно плохо. Но нужно честно указать, что уже существует и чем предлагаемое решение отличается.

---

### 9. Проведи adversarial reviewer pass

После scoring matrix проведи жёсткую проверку каждой серьёзной идеи с позиции критика.

Для каждой идеи reviewer обязан ответить:

```txt
strongest argument against it
how it can fail
how it can overfit or mislead
what evidence would kill the idea
final decision: KEEP / REJECT / REWRITE
```

Проверяй идеи жёстко. Не защищай их автоматически.

---

### 10. Переранжируй идеи только после reviewer pass

После adversarial reviewer pass:

- убери идеи с решением `REJECT`;
- перепиши или понизь идеи с решением `REWRITE`;
- заново отсортируй оставшиеся идеи;
- учитывай не только `Total`, но и выводы reviewer pass.

---

### 11. Выбери финальный TOP-3

Выбери только 3 лучшие идеи.

Финальный выбор делай только после:

- изучения source-of-truth файлов;
- фильтрации 20–30 сырых идей;
- scoring matrix;
- project evidence/gap check;
- novelty/prior-art check;
- adversarial reviewer pass;
- финального переранжирования.

---

### 12. Для каждой идеи из TOP-3 напиши план реализации

Для каждой из финальных 3 идей укажи:

```txt
exact implementation plan
exact files/areas likely affected
minimum experiment/test
success metrics
failure criteria
validation/anti-overfitting guard
```

План должен быть конкретным, а не абстрактным.

Плохой пример:

```txt
Улучшить тесты и проверить качество.
```

Хороший пример:

```txt
Добавить regression-test для сценария X в файле Y, где входные данные Z должны приводить к результату N. Успех — тест стабильно проходит на 20 исторических кейсах без ухудшения baseline.
```

---

## Формат ответа

Ответ должен строго использовать такую структуру:

```txt
A. Понимание проекта

B. Слабые места

C. Таблица статусов сырых идей

D. Scoring matrix серьёзных идей

E. Проверка evidence / gap по проекту

F. Novelty / prior-art check

G. Adversarial reviewer pass

H. Финальный рейтинг

I. Планы реализации TOP-3
```

---

## Жёсткие ограничения

- Отвечай только на русском языке.
- Не переходи на английский, кроме названий файлов, команд, терминов, статусов и формулы.
- Не предлагай идеи без проверки по файлам проекта.
- Не делай вид, что что-то реализовано, если не нашёл доказательство.
- Не выбирай TOP-3 до scoring matrix и reviewer pass.
- Не пропускай причины для `REJECT`, `MERGE`, `DEFER`.
- Не используй общие фразы без конкретных файлов, тестов или критериев.
- Не продолжай после раздела `I`.

После выполнения остановись и жди моего подтверждения.
