# Документ требований: AI Music Chat

## Введение

AI Music Chat — это функция чат-интерфейса для поиска похожих музыкальных моментов по всей библиотеке. Пользователь указывает трек и временной диапазон (например, "00:29 - 00:35"), задаёт вопрос на естественном языке, и система находит все похожие фрагменты в библиотеке с указанием точных таймстампов.

## Глоссарий

- **Chat_Interface**: Компонент пользовательского интерфейса для ввода запросов и отображения результатов поиска похожих сегментов
- **Query_Parser**: Модуль парсинга пользовательских запросов для извлечения ссылки на трек и временного диапазона
- **Segment_Index**: FAISS индекс эмбеддингов сегментов/фрагментов треков для поиска похожих моментов
- **Similarity_Search_Service**: Сервис поиска похожих сегментов по эмбеддингам
- **Time_Range**: Временной диапазон в формате "MM:SS - MM:SS" или "Ns - Ms"
- **Segment_Embedding**: 1280-мерный вектор, представляющий аудио-характеристики сегмента трека
- **Match_Result**: Результат поиска, содержащий трек, таймстамп и оценку схожести

## Требования

### Требование 1: Парсинг запросов пользователя

**User Story:** Как пользователь, я хочу вводить запросы на естественном языке с указанием временного диапазона, чтобы система понимала, какой момент трека я хочу найти.

#### Критерии приёмки

1. WHEN пользователь вводит запрос с временным диапазоном в формате "MM:SS - MM:SS" THEN Query_Parser SHALL извлечь start_time и end_time в секундах
2. WHEN пользователь вводит запрос с временным диапазоном в формате "Ns - Ms" (например, "29s - 35s") THEN Query_Parser SHALL извлечь start_time и end_time в секундах
3. WHEN пользователь вводит запрос без указания трека THEN Query_Parser SHALL использовать текущий воспроизводимый трек как источник
4. WHEN пользователь указывает трек по имени или ID THEN Query_Parser SHALL найти соответствующий трек в базе данных
5. IF временной диапазон некорректен (start >= end или отрицательные значения) THEN Query_Parser SHALL вернуть ошибку с описанием проблемы
6. WHEN временной диапазон выходит за пределы длительности трека THEN Query_Parser SHALL ограничить end_time длительностью трека

### Требование 2: Индексация сегментов для поиска

**User Story:** Как система, я хочу иметь индекс эмбеддингов всех сегментов, чтобы быстро находить похожие моменты.

#### Критерии приёмки

1. THE Segment_Index SHALL хранить эмбеддинги всех проанализированных фрагментов (Fragment) с их метаданными
2. WHEN новый фрагмент анализируется THEN Segment_Index SHALL автоматически добавить его эмбеддинг в индекс
3. WHEN фрагмент удаляется THEN Segment_Index SHALL удалить соответствующий эмбеддинг из индекса
4. THE Segment_Index SHALL поддерживать поиск k ближайших соседей по L2-расстоянию
5. THE Segment_Index SHALL сохраняться на диск и загружаться при перезапуске системы

### Требование 3: Поиск похожих сегментов

**User Story:** Как пользователь, я хочу находить все похожие моменты в библиотеке на основе выбранного фрагмента, чтобы открывать новую музыку.

#### Критерии приёмки

1. WHEN пользователь отправляет запрос с временным диапазоном THEN Similarity_Search_Service SHALL извлечь эмбеддинг указанного сегмента
2. WHEN эмбеддинг сегмента получен THEN Similarity_Search_Service SHALL найти top-N похожих сегментов в Segment_Index
3. THE Similarity_Search_Service SHALL возвращать для каждого результата: track_id, track_title, artist, start_time, end_time, similarity_score
4. THE Similarity_Search_Service SHALL исключать сегменты из того же трека, что и исходный запрос
5. WHEN в индексе нет похожих сегментов (similarity_score < threshold) THEN Similarity_Search_Service SHALL вернуть пустой список с информационным сообщением

### Требование 4: Чат-интерфейс

**User Story:** Как пользователь, я хочу удобный чат-интерфейс для ввода запросов и просмотра результатов, чтобы взаимодействие было интуитивным.

#### Критерии приёмки

1. THE Chat_Interface SHALL отображать поле ввода для текстовых запросов
2. WHEN пользователь отправляет запрос THEN Chat_Interface SHALL отобразить сообщение пользователя в истории чата
3. WHEN система обрабатывает запрос THEN Chat_Interface SHALL отобразить индикатор загрузки
4. WHEN результаты получены THEN Chat_Interface SHALL отобразить список Match_Result с информацией о треке и таймстампе
5. THE Chat_Interface SHALL отображать текущий воспроизводимый трек и его прогресс для удобства указания временного диапазона
6. WHEN пользователь нажимает на результат THEN Chat_Interface SHALL начать воспроизведение трека с указанного таймстампа

### Требование 5: Воспроизведение результатов

**User Story:** Как пользователь, я хочу сразу прослушать найденные похожие моменты, чтобы оценить их релевантность.

#### Критерии приёмки

1. WHEN пользователь кликает на Match_Result THEN система SHALL начать воспроизведение трека с start_time найденного сегмента
2. THE Chat_Interface SHALL отображать мини-плеер для каждого результата с возможностью воспроизведения
3. WHEN воспроизведение сегмента завершается (достигнут end_time) THEN система SHALL остановить воспроизведение или перейти к следующему результату
4. THE Chat_Interface SHALL позволять пользователю добавить понравившийся результат в избранное (like)

### Требование 6: API для поиска похожих сегментов

**User Story:** Как разработчик, я хочу иметь API endpoint для поиска похожих сегментов, чтобы интегрировать функцию в приложение.

#### Критерии приёмки

1. THE API SHALL предоставлять endpoint POST /api/chat/search для поиска похожих сегментов
2. WHEN запрос содержит track_id, start_time, end_time THEN API SHALL вернуть список похожих сегментов
3. WHEN запрос содержит параметр limit THEN API SHALL ограничить количество результатов указанным значением
4. WHEN запрос содержит параметр min_similarity THEN API SHALL фильтровать результаты по минимальному порогу схожести
5. IF track_id не найден THEN API SHALL вернуть ошибку 404 с описанием
6. IF временной диапазон некорректен THEN API SHALL вернуть ошибку 422 с описанием валидации

### Требование 7: Сохранение истории чата

**User Story:** Как пользователь, я хочу видеть историю своих запросов, чтобы вернуться к предыдущим результатам.

#### Критерии приёмки

1. THE Chat_Interface SHALL сохранять историю запросов и результатов в локальном хранилище браузера
2. WHEN пользователь открывает Chat_Interface THEN система SHALL загрузить и отобразить предыдущую историю
3. THE Chat_Interface SHALL позволять очистить историю чата
4. WHILE история чата превышает 100 сообщений THEN система SHALL удалять самые старые сообщения
